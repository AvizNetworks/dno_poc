1 · The idea / 15

What is DPF?

DPF = DOCA Platform Framework (NVIDIA). Kubernetes-native lifecycle management for BlueField-3 DPUs.

  • You declare the desired state (which OS image, which cluster, which workloads) as Kubernetes objects.
  • DPF makes it happen: flashes the BFB → boots the BF3 → joins it to a cluster → deploys services (HBN) onto it.
  • One control point for many DPUs — no SSH to each box. The same kubectl drives 1 or 100.
2 · Foundation / 15

Kubernetes in 60 seconds

CLUSTER
control plane (API + scheduler + etcd) that runs & tracks everything
NODE
a machine running kubelet that workloads land on
POD
1+ containers sharing one network identity
CONTAINER
a process isolated by Linux namespaces + cgroups
  • Declarative: you describe the end state; controllers reconcile to it.
  • kubectl is the remote control — talks to the cluster API, not the machines.
  • DaemonSet = "one pod on every node" → deploy once, runs fleet-wide.

DPF builds on these primitives — the BF3 becomes a node, HBN becomes a pod.

3 · NVIDIA's building blocks / 15

What NVIDIA built for DPF

The DPF Operator + sub-controllers (provisioning · dpuservice · kamaji-cm · servicechainset), driven by custom resources you declare:

DPFOperatorConfig

Bootstraps the whole system on the DPF VM.

BFB

The DPU OS image (DOCA bf-bundle) served to the BF3.

DPUFlavor

How to flash: NIC firmware, hugepages, SubFunctions, config files.

DPUCluster

A per-DPU virtual k8s control plane, run by Kamaji as pods on the DPF VM.

DPU / DPUNode / DPUDevice

The physical BF3 being provisioned and tracked.

DPUService

Workloads pushed onto DPUs — CNI, and HBN.

7 · Host ports / 15

Create the workload ports (host VFs)

SR-IOV VFs on the x86 host are the ports your VMs / workloads plug into. One command creates and names them.

# on the x86 host, after HBN is up
sudo ./dpf/scripts/setup_host_vfs.sh            # → vf0 .. vf7
sudo ./dpf/scripts/setup_host_vfs.sh --persist  # survive reboot
  • Auto-detects the BlueField-3 PFs by PCI id — no NIC names to look up.
  • Names them vf0..vf3 (PF0) and vf4..vf7 (PF1).
  • Refuses to run with >1 BF3 on a host (avoids ambiguous naming).

11 · Demo — the payoff / 15

Reach FRR with kubectl — no SSH

POD=$($D get pod -n doca-hbn -o jsonpath='{.items[0].metadata.name}')

# drop into FRR's CLI (zebra/bgpd/staticd answer through vtysh)
$D exec -it -n doca-hbn $POD -- vtysh

doca-hbn# show interface brief        # p0_if, pf0vf0_if …
doca-hbn# show ip route               # zebra's RIB

# one-shot, no shell:
$D exec -n doca-hbn $POD -- vtysh -c "show interface brief"

kubectl exec rides the cluster → BF3 kubelet → into the HBN container. Same command for any DPU in the fleet.

12 · Current scope & caveats / 15

What works today — and what doesn't yet

  • One DPU per DPF VM — validated for a single BF3.
  • Flashing is via rshim, not Redfish. The OS flash goes through the x86 host's PCIe rshim (--rshim-install), so the x86 host must be reachable with a working rshim. Redfish works only for a genuine BFB version change; S4 was already on the target version, so rshim was required.
  • Fresh-flash first boot is hands-on — console password, dhclient oob_net0, enable sfc.service (all in QUICKSTART.md).
